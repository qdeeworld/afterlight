# Integrate Afterlight recovery

`@afterlight/recovery` packages the same client primitives used by Afterlight:
per-vault keys and encrypted backups, Cairo-compatible authorizations, STRK20
action construction, relay payloads, and structural exit validation.

It is a typed ESM library, not a second recovery contract or a hosted wallet.
The current package is distributed as an installable tarball. These instructions
do not require or claim an npm registry release.

## Install and verify

Use Node.js `22.13.1` and the repository's locked dependencies:

```sh
git clone https://github.com/qdeeworld/afterlight.git
cd afterlight
npm --prefix client ci
npm --prefix client run test:package
cd client
npm pack
cd ..
node examples/recovery-integration/verify.mjs "$PWD/client/afterlight-recovery-0.1.0.tgz"
```

In your own ESM application, install that archive:

```sh
npm install --ignore-scripts /absolute/path/afterlight-recovery-0.1.0.tgz
```

The [consumer example](../examples/recovery-integration/README.md) verifies an
installation in a temporary directory outside this checkout. It compiles against
the published entrypoints and TypeScript declarations, audits the locked dependency
tree, bundles a browser helper, and checks local authorization and backup behavior. It uses synthetic state and
ephemeral application keys: it neither contacts a wallet nor submits a transaction.

## What another application can reuse

| Module | Integration purpose |
| --- | --- |
| `@afterlight/recovery/keys` | Create an independent per-vault application key; export and restore password-encrypted backups; sign and verify hashes. |
| `@afterlight/recovery/messages` | Construct the exact domain-separated authorization hash understood by Cairo. |
| `@afterlight/recovery/actions` | Encode funding, cancellation and claim actions for the STRK20/Afterlight boundary. |
| `@afterlight/recovery/relay` | Construct and validate supported neutral-control payloads. |
| `@afterlight/recovery/exit-preflight` | Validate prepared-exit structure and bind destination, action and proof-envelope fields. |
| `@afterlight/recovery/setup-authorization` | Bind first-use consent to the final package for the pinned Mainnet deployment. |
| `@afterlight/recovery/encoding` | Normalize and validate felts and bounded integers. |

The root entrypoint exports these modules too. A narrow import makes the
integration boundary explicit:

```ts
import { authorizationHash, type HeartbeatAuthorization }
  from "@afterlight/recovery/messages";

export function heartbeatDigest(auth: HeartbeatAuthorization): string {
  return authorizationHash(auth);
}
```

The runnable example provides a more complete control-preparation helper with
state-bound payloads, role matching and expiry checks. A hash or locally valid payload is not
permission to act: the deployed contract remains authoritative when it executes.

## Cairo interface

The public [`IAfterlight` interface](../src/afterlight.cairo) and
[shared Cairo types](../src/common.cairo) describe the same deployed contract.
Its ABI is generated by `scarb build`.

| Contract method | Caller and effect |
| --- | --- |
| `get_config`, `get_vault`, `get_locked_by_token` | Read chain configuration, current reserve state and liabilities before preparing an action. |
| `heartbeat`, `request_recovery`, `veto` | Any submitter can relay a valid application-key authorization. The role key, current state, epoch, nonce and timing determine permission. |
| `privacy_invoke` | Only the configured STRK20 pool may call it. Funding, cancellation and claim enter through this boundary; it is not a direct public transfer shortcut. |
| `sync_funding_checkpoint` | Public accounting checkpoint. This alone does not reserve hosted sponsor capacity or fund a reserve. |

Before requesting a signature, bind the actual chain, contract, vault, token,
amount, expected state, epoch, role nonce and expiry. Claim and cancellation must
also bind the exact destination note. Re-read state before execution; never reuse
a signature after a veto, successful action or expiry.

## Connecting a wallet or relayer

The installed library does not automatically request a wallet connection,
access funds, generate a STRK20 proof, or broadcast anything. Live integration
still needs the user's Ready/STRK20 wallet, current chain reads, explicit wallet
approvals, and a supported submission route. `PrivateExitPreflight` takes
caller-supplied ports; invoking them can contact those configured services.

Afterlight's hosted sponsor is origin-allowlisted and capacity-limited. Importing
the SDK does **not** grant another website access to that service. A separate
application needs a supported relayer/origin arrangement or its own reviewed
infrastructure and fee backing. Do not embed a sponsor key in a browser.

The first-use setup hash intentionally pins Mainnet, the current contract and
classes, pool, sponsor and STRK token. It is not a generic authorization domain
for a different deployment. The existing reserve denomination is also fixed by
the contract. Changing either requires a separate integration and release review.

Structural exit checks do not cryptographically verify opaque proofs. Canonical
Starknet admission authenticates proof facts, and the STRK20 pool and Afterlight
enforce settlement. Only a successful chain receipt and the expected state change
establish completion. See [architecture](ARCHITECTURE.md),
[first-use compatibility](FRESH_WALLET_COMPATIBILITY.md), and the
[threat model](THREAT_MODEL.md) for those boundaries.

## Package guarantees

The package test checks an exact archive allowlist, all declared runtime/type
entrypoints, the MIT license, unchanged setup-authorization declarations, and
byte-identical repeated packing. The archive excludes repository operator tools,
test fixtures, local configuration, credentials and install-time hooks.

CI also installs the archive into the separate consumer and executes its checks.
This establishes reproducible developer integration; it does not claim that a
third-party product has already adopted the SDK.
